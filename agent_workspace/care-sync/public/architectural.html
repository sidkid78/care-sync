Architectural Integrity and Health Data Privacy Framework: The Care-Sync Security Blueprint

1. Framework Governance and the Privacy-by-Design Philosophy

In the specialized landscape of family care coordination, "Privacy-by-Design" is more than a compliance mandate; it is a strategic imperative. For a Principal Security Architect, technical security is the primary mechanism for establishing stakeholder trust when handling Protected Health Information (PHI). The Care-Sync platform is engineered to minimize the attack surface by embedding security controls directly into the architectural layers rather than treating them as an external perimeter.

The security philosophy synthesizes Core Platform Services with rigorous Cross-Cutting Concerns. By leveraging a hybrid architecture of Next.js and Supabase, we ensure that the "secure and scalable backbone" is not just a marketing claim but a technical reality. A critical advantage of the Next.js App Router is the implementation of Server Components, which allows for data fetching to occur entirely on the server side. This architecture prevents the exposure of sensitive API keys and business logic to the client-side environment, fundamentally reducing the potential for exploitation.

The primary architectural pillars include:
  • Frontend: Next.js Server Components for secure data fetching and Client Components for controlled interactivity.
  • Backend & Database: Supabase (PostgreSQL) providing integrated identity management, Row Level Security (RLS), and managed storage.
  • AI Orchestration: Asynchronous worker services utilizing AWS SQS for message queuing and AWS Lambda/ECS for compute-intensive processing of health data.
  • Cross-Cutting Concerns: Centralized KMS Management, Secrets Management, and continuous Monitoring & Logging to ensure system-wide visibility.

This philosophy is enforced through a transition from high-level governance to granular, database-level isolation, ensuring that every byte of data is protected by rigorous access control policies.

2. Granular Access Control: Row Level Security (RLS) and Multi-Tenancy

In a multi-tenant health platform, Row Level Security (RLS) is the primary defense against Insecure Direct Object Reference (IDOR) vulnerabilities. Without RLS, data leakage between family groups represents an existential compliance risk. By enforcing access policies at the database tier, we ensure that data isolation is a property of the data itself, not just the application logic.

Database Schema & RLS Enforcement Policy

Table Entity Security Function Access Justification
profiles RLS Policy Multi-tenant isolation: Ensures users can only view or update their specific profile linked to their auth.users ID.
families RLS Policy IDOR Mitigation: Restricts access to family group metadata exclusively to authenticated members of that specific family.
family_members RLS Policy RBAC Enforcement: Controls permissions (e.g., Primary Caregiver vs. Member) within the tenant to prevent unauthorized administrative actions.
shifts RLS Policy Data Leakage Prevention: Ensures scheduling and care duties are never exposed to users outside the designated family group.
feed_posts RLS Policy Privacy Preservation: Restricts the visibility of daily activity and health status updates to verified, authenticated family members.

A critical component of this provisioning is the handle_new_user PostgreSQL trigger. This trigger is attached to the auth.users table; upon a new user insertion, it automatically creates a corresponding entry in the profiles table with a default role. This automation is superior to manual profile creation as it eliminates the risk of "orphaned" users who lack security policies, ensuring that every user is immediately governed by the "least privilege" model.

3. Cryptographic Sovereignty: "The Vault" and Client-Side Encryption

For high-sensitivity documents, Care-Sync implements "The Vault," a zero-knowledge storage solution. By utilizing client-side encryption, we shift the security perimeter from our servers to the user's device. This ensures that even in the event of a total server-side compromise, the underlying PHI remains undecipherable.

The Vault Encryption/Decryption Lifecycle

Upload Sequence
1. Key Derivation: The user provides a password (which is never transmitted to or stored on the server). The client-side Web Crypto API generates a unique encryption salt.
2. PBKDF2 Stretching: A strong AES-256 GCM key is derived from the password and salt using the PBKDF2 algorithm, providing high resistance to brute-force attacks.
3. Authenticated Encryption: The file is encrypted locally. The system generates a unique Initialization Vector (IV).
4. Integrity Verification: A SHA256 checksum is calculated for the encrypted blob.
5. Secure Transmission: The encrypted blob is uploaded to Supabase Storage. The salt, IV, and checksum are stored as metadata in the vault_documents database table.
Download Sequence
1. Retrieval: The client fetches the metadata and a time-limited pre-signed URL for the encrypted file.
2. Integrity Check: The client downloads the blob and verifies it against the stored SHA256 checksum.
3. Local Decryption: The user re-enters their password. The client re-derives the AES key using the stored salt and decrypts the content locally using the IV.

EVALUATION OF PROTOCOLS: The use of AES-256 GCM is a strategic choice for HIPAA compliance because it provides "authenticated encryption." This means the protocol not only ensures confidentiality but also detects if the data has been tampered with.

4. Secure AI Orchestration and Data Ephemerality

Integrating Agentic AI with health data requires a "Zero-Trust" approach to external APIs. We map the data flow for features like "Doctor Digest" and "Med-Cabinet Scanner" to ensure that PHI is never permanently stored in a raw or unencrypted state within the AI pipeline.

AI Processing Pipeline (Doctor Digest & Med-Cabinet Scanner)

  1. Ingestion: Raw audio (Doctor Digest) or images (Med-Cabinet) are uploaded via pre-signed URLs to private storage buckets.
  2. STT/OCR Phase: An asynchronous worker (AWS Lambda) retrieves the file, processes it through Gemini 2.5 Flash or Google Cloud Vision, and stores a raw transcript/text in an encrypted, temporary table.
  3. LLM Phase: A second worker sends the transcript to Gemini 2.5 Flash via an encrypted TLS connection for summarization or drug conflict identification.
  4. Encrypted Persistence: The structured result is encrypted using KMS-managed keys and stored in the database, triggering a Realtime update to the family.
Data Ephemerality and Training Policies:

A cornerstone of this architecture is Data Ephemerality. Once the final summary or drug interaction warning is generated, the platform automatically deletes raw audio files, images, and intermediate transcripts. Furthermore, Care-Sync utilizes Enterprise API policies with Gemini and Google Cloud, which contractually guarantee that user data is excluded from model training sets.

5. Infrastructure Resilience and Compliance Guardrails

System resilience is a prerequisite for security; a system that is unavailable is not secure. Our architecture utilizes Dead-Letter Queues (DLQs) within the SQS pipeline to capture failed AI messages, ensuring that sensitive data is not lost or mishandled during transient service failures.

The "God Key" Risk Mitigation: The platform maintains a strict distinction between standard user access and administrative tasks. While RLS governs 99% of data interactions, tasks such as Stripe webhook synchronization require the Supabase Service Role Key. We treat this as a "god key" that bypasses all RLS policies. Consequently, its use is restricted strictly to server-side logic (Edge Functions) and is never exposed to the client-side environment.

This blueprint represents a high-integrity architecture where cryptographic sovereignty and database-level isolation converge, ensuring Care-Sync is fully prepared for the rigorous demands of high-stakes healthcare environments.
